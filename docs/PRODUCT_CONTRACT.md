# TextSnap product contract

Read this before changing, reviewing, or troubleshooting capture, hotkey, OCR, clipboard, menu, Settings, app-icon artwork, or "Check for Updates".

## One sentence

Press a shortcut, drag a region on screen, the text in it lands in the clipboard.

## Flow

1. User presses the global shortcut (factory: Command Shift 2) or clicks the menu bar icon (left click), or picks Capture from the menu / settings.
2. The system selector appears (`screencapture -i -s`). Esc cancels; nothing happens.
3. On-device Vision reads the captured PNG (accurate level, revision 3, language correction, automatic language detection, Chinese-varieties-first language order). No network.
4. Non-empty text goes straight to the general pasteboard; a short sound confirms. No result window.
5. Empty result, capture failure, or missing screen-recording permission shows a one-shot explanatory alert with a way forward. Never a silent failure, never a retry loop.

## Hotkey

- Factory default is Command Shift 2. User can record a new combination, clear it, or restore the default. Settings apply immediately and survive restart.
- A combination already taken fails loudly in settings; system-reserved combinations are refused with a reason.
- A second press while a capture is already in flight is dropped, never queued.

## Permission

- Screen recording is pure TCC. First capture triggers the system prompt; the usage description explains the capture-then-recognize purpose.
- Denied state is a first-class UI state: what is missing, what breaks, an Open System Settings button, and an explicit retry. Coming back from settings re-checks automatically.
- No other system permission is requested.

## Startup and first-use reliability (2026-10-24)

Reported symptom: after boot, the shortcut seemed unusable for one to two minutes. Measured cause, reproduced on this Mac: Vision's first text-recognition pass in a process loads the macOS 27 recognition model and took 63.5 s in a standalone probe and 91.9 s inside TextSnap; the same request took 0.23 s once the model was loaded. The old code ran that first pass synchronously on the main actor, so recognition, the status menu and the global-shortcut callback all froze for that window. The model load is per process, so it also affects first use after a relaunch, not just after boot.

Adopted contract:

- The global shortcut is registered in `applicationWillFinishLaunching`, before the status item, Sparkle, launch-at-login state or any other launch work. A failed registration retries with bounded backoff (1 s through 120 s) and re-asserts after wake, screen wake, unlock, session activation, and at 5/30/90 s while a login session settles. User-recorded conflicts still fail loudly in Settings and are not retried behind the user's back.
- Text recognition never runs on the main actor. Vision's `supportedRecognitionLanguages()` result is cached for the process, and a launch-time warm-up runs one tiny recognition off-main so the first real capture does not pay the cold-model cost.
- Sparkle starts about two seconds after launch, never in the pre-launch path. Launch-at-login state is read off-main and cached; status menus never synchronously call `SMAppService` (macOS rebuilds them during login).
- Diagnostics are privacy-safe: `log show --last boot --predicate 'subsystem == "top.caozc.TextSnap"' --style compact` shows launch phases, registration attempts/retries, every delivered shortcut press, selector duration, OCR duration and character count. Recognized text and clipboard contents are never logged.

Acceptance: on the installed signed build, the shortcut must respond during the warm-up window (log `pressed` and a selector process within ~1 s), and the first capture after launch must not block the menu or a second press. The warm-up duration is recorded so a future macOS regression is measurable.

## OCR reliability, hotkey resilience and observability (2026-11-25)

Reported symptoms on macOS 27.3 (`26C5047e`, M1 Pro): (1) global shortcut repeatedly failed to bring up capture, and (2) every capture failed with `"The capture or recognition failed. Try again with a larger, sharper region."`.

Live-log and empirical probe diagnosis (10 trials) on macOS 27.3 (`26C5047e`, M1 Pro) on the installed 0.2.8 process:
- The previous `320×64` (`height == 64`) launch warm-up image triggered a `28–137 s` `ANECompilerService` compilation (peaking at 2.2 GB swap) and poisoned Vision's in-process E5RT runtime 6/6 times (`CRImageReaderError.e5rtError("e5rt_execution_stream_operation_create_precompiled_compute_operation_with_options call failed", 13)`), causing every subsequent `.accurate` recognition—even `.cpu` and `usesCPUOnly`—to fail in `5–89 ms`. Starting with a `512×256` bilingual image (`"TextSnap 中文测试 12345"`) succeeded 6/6 times with zero `e5rtError 13` and subsequent calls completed in `82–314 ms`. (`.fast` lacks Chinese support (`hasZh=false`), so it cannot substitute for `.accurate`.)
- While that first capture waited `59.6 s` behind `warmUp()` and then blocked on `NSAlert.runModal()`, `CaptureEngine.isCapturing` remained `true` and dropped 15 consecutive shortcut presses (`trigger dropped: capture already in flight`).
- `/usr/sbin/screencapture` can exit `0` with an error written only to `stderr` and no output file, and `waitUntilExit()` blocked a Swift cooperative thread without sleep/resign cancellation.

Adopted contract:
- **E5RT-safe, non-blocking Vision pipeline & headless worker recovery**: `TextRecognizer` pads crops smaller than `256×160` onto a centered `>= 320×192` white sRGB canvas before Vision execution, tries `.gpu` then `.cpu` via `setComputeDevice(_:for: .main)` with 8-bit sRGB normalization fallback, and runs without a global serialization lock or launch-time warm-up (updated 0.2.10: live logs showed launch warm-up triggered a 65 s `ANECompilerService` compile that queued real user captures behind it). If an in-process E5RT error ever occurs, `TextRecognizer` marks the process poisoned and transparently routes subsequent URL recognitions through a headless `TextSnap --ocr-once <imagePath>` worker process (dispatched in `TextSnapEntry.main()` before AppKit initializes).
- **Non-locking capture & non-blocking selector**: `CaptureEngine` only drops re-entrant hotkey presses while `isSelecting` (`checkingPermission` or `selecting`), immediately releasing the shortcut guard as soon as `screencapture` returns. Background OCR uses `recognitionGeneration` superseding so a newer shortcut press immediately opens the crosshair and supersedes any slower in-flight OCR pass; modal alerts release `isSelecting` before `runModal()` and dismiss stale alerts on a new trigger. `CaptureEngine` caches confirmed `granted == true` Screen Recording permission (refreshed off-main on launch and `didBecomeActive`, and invalidated immediately on selector failure; `false` is never cached so B6 first-time grant still works immediately), spawns `/usr/sbin/screencapture` off `@MainActor`, and logs `dispatchMs` from hotkey press to capture entry. The confirmation chime uses `AudioToolbox` (`AudioServicesCreateSystemSoundID` + `AudioServicesPlaySystemSound` on `/System/Library/Sounds/Glass.aiff`, fallback `kSystemSoundID_UserPreferredAlert`) dispatched asynchronously on a dedicated background serial queue, never AppKit `NSSound` on `@MainActor` (live OSLog showed `NSSound.play()` synchronously initialized CoreAudio HAL / `AVAUVoiceIO` / `SpatializationManager` on the main thread and stalled for ~14.9 s on macOS 27.3). `CaptureTextIntent` returns the actual outcome rather than stale `lastText`, and `ScreenCapture` uses `terminationHandler` + async `stderr` capture + task cancellation on `willSleepNotification` / `sessionDidResignActiveNotification`.
- **Hotkey resilience**: `HotkeyManager` suspends the active hotkey during Settings shortcut recording (and restores it on cancel/invalid key or window key resignation), validates `EventHotKeyID.signature`, adds coalesced 600 ms post-wake/unlock settle re-assertion, and logs `IsSecureEventInputEnabled()` plus Carbon `OSStatus` names. `TextSnapApp` routes `⌘Q` through `TerminationGuard`, and `SettingsView` checks screen-capture permission off-main.
- **Dual-sink observability logs**: Every `lifecycle`, `hotkey`, `capture`, and `settings` event writes both to Unified Logging (`subsystem == "top.caozc.TextSnap"`) and to a rotating privacy-safe local file at `~/.config/textsnap/logs/textsnap.log` (`$XDG_CONFIG_HOME` aware; directory `0o700`, file `0o600`, 2 MB × 3 backups). Logs record startup banner, correlation IDs (`id=#N`), capture source, phase/duration on dropped triggers, selector exit/stderr/image dimensions, OCR compute device/attempts/duration/character count, and settings I/O errors; recognized text, images, and clipboard contents are never logged.
- **Reusable background E2E**: `Tests/E2E/` runs focus-safe, cursor-safe `macos-e2e` tests against `/Applications/TextSnap.app` using `--e2e-testing --e2e-root <tmp> --e2e-capture-image <fixture.png>`, keeping `~/.config/textsnap/` and production `NSPasteboard.general` untouched.

## Login launch silence (owner report 2026-11-15)

The owner reported that after a reboot, with the menu-bar icon hidden and Launch at Login on, TextSnap opened its Settings window by itself. Root cause: the login-item check ran in `applicationWillFinishLaunching`, before AppKit dispatches the open-application Apple Event, so it always read false; the hidden-icon recovery rule then treated the login start as a user cold launch. An `SMAppService.mainApp` login start may additionally arrive with no launch event at all.

Classify the launch in `applicationDidFinishLaunching` through `LaunchClassification`: a legacy `keyAELaunchedAsLogInItem` marker or a launch with no Apple Event counts as a login launch and stays silent. Finder, Dock, Spotlight and `open` deliver the open-application event and still present Settings when the icon is hidden, and `applicationShouldHandleReopen` still answers a user reopen. The lifecycle log records `launchEvent`, `loginLaunch`, `iconVisible` and `recoveryWindow` so the next real login can be checked without guessing.

The check now reads the flat key and skips the launch for a hidden icon, matching the product rule. The published artifact is unaffected. After the fix, `scripts/release.py --verify-only --no-install` re-downloaded and re-hashed the published assets and recorded `published_verified` with no error.

## Diagnostics and release notes

Release notes live in [CHANGELOG.md](../CHANGELOG.md); the publisher embeds the matching English and complete Simplified Chinese section in both Sparkle and GitHub. The archive explicitly builds arm64 and x86_64 for the supported Mac architectures. The existing Vision results property is already a typed optional array in the installed SDK, so its no-op conditional downcast is removed without changing recognition order or output.

The Sparkle 2.10.0 runtime warning about background scheduled checks without gentle reminders is retained for this settings revision. Origin: the existing standard updater has no user-driver delegate. Sparkle's [background-app behavior and examples](https://sparkle-project.org/documentation/gentle-reminders/) explain that scheduled alerts appear behind other apps after launch; implementing its background reminder example would add Dock/notification behavior beyond this settings task and the current screen-recording-only permission contract. Manual Check for Updates still uses Sparkle's standard user-initiated UI. Residual risk: a background-only user may miss a scheduled alert. Follow-up: design an in-menu reminder or adopt a separately approved background reminder policy; do not merely return true from the support flag without providing a reminder.
